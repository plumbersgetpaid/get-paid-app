Why the data matters

Our users are tradespeople; the app also stores data about their customers — homeowners' names, addresses, phone numbers, and photos taken inside private homes. Under UK GDPR we are the processor for that data. The single question behind this whole engagement: can one business's data ever reach another business, or the public?

Known-open items — handed to you, not hidden
  • 26 unchecked database writes (child-row deletes, log inserts — the recoverable tail of a swept class). Listed in CLAUDE.md; we'd like your judgement on which matter.
  • Storage authorisation is app-enforced: signed URLs are minted after app-level access checks. Moving to storage-level policies keyed on business_id would be database-enforced — needs an object-path migration. Opinion wanted: worth it now?
  • Legacy session tokens: pre-versioning 3-part tokens still verify as version 0 until expiry (≤30 days from the change). Known, time-limited.
  • VAPID push keypair rotation pending (private key was exposed to an internal tool transcript once; blast radius is push-send only).
  • supabase/schema.sql is stale — the live DB is the source of truth; a fresh deploy from the repo would not stand up correctly.
Where we want your hours
  1. The custom auth design itself HMAC cookie sessions, the proxy.js gate, permission model (owner/manager/subcontractor + per-capability flags), the public-paths list. We built it; we want someone hostile to read it.
  2. The 21 service-role routes These bypass RLS and must scope themselves. Our rule: reading other businesses' rows can be fine; anything from one business reaching another is a leak. Check each against it — one real leak of this class was found and fixed internally.
  3. Offline sync abuse The outbox replays queued actions with idempotency claims. Try to break it: request-ID squatting across businesses, replay with mutated payloads, queue poisoning, the expired-session hold path.
  4. Uploads and media Photo uploads (multipart, compressed client-side), signed-URL lifetimes, the export zip builder, PDF generation fetching signed URLs server-side.
  5. GDPR posture as a whole Processor duties, the retention rule (30 days; Stripe records 6 years), the deletion job's completeness, on-device data handling — plus a solicitor's read of /privacy and /terms (drafted in-house, never reviewed by counsel; liability cap and governing-law clauses in particular).
Materials and access
  • Private GitHub repo (read access on request) — CLAUDE.md at the root is an honest, current map of the system including its known weaknesses; start there.
  • The isolation harness and its 135 checks, runnable against any deployment.
  • A dedicated test business with owner and subcontractor logins, on production (which holds only test data pre-launch).
  • All internal audit notes and the reasoning behind each fix, in the git history.

Ground rules: production carries no real customer data yet, so testing can be intrusive — but coordinate anything destructive (the deletion cron is real) and don't degrade the Stripe live-mode account. Email volume goes through a shared Resend domain; go easy on sends.

We expect this is roughly 2–4 days of work; tell us if you read it differently, and quote fixed-price if you can.
